# COFA 서술형 사전 대비

사용자가 요청한 사전 연습에서만 사용한다. 서술형 실전 응시 중에는 출제·답변 지원을 진행하지 않는다. 프로젝트를 읽기 전용으로 조사하고 질문과 피드백은 대화에서만 전달한다. 코드, 문서, 설정을 수정하거나 연습 상태를 파일에 저장하지 않는다.

## SET — 질문 출제

사용자가 AI와 함께 구현한 시스템의 핵심 설계 판단, 선택 이유, 대안의 장단점, 전체 구조와 예외 동작을 이해하는지 확인한다.

1. 대상 프로젝트의 실제 코드와 루트의 `DEFENSE_LOG.md`를 읽는다. 설계 변경, AI 제안 확인 또는 검증 경위를 더 알아야 할 때 관련 `WORKLOG.md`를 읽는다. 읽을 코드나 확인된 코드 위치가 없으면 필요한 범위를 알려주고 출제를 보류한다.
2. 진입점부터 실제로 호출되는 함수와 데이터·상태 변경을 따라간다. 시스템 전체나 핵심 흐름에 영향을 주는 설계 선택, 단계 연결, 책임 경계와 실패 동작을 우선한다. 사소한 함수 구현이나 문법은 질문 주제에서 제외한다.
3. 각 질문을 실제 설계 선택이나 시스템 동작에 연결하고, 관련 경로의 `파일:줄`을 직접 열어 확인한다. 코드 위치를 붙였더라도 일반적인 CS 지식, 용어 정의, 교과서적인 장단점만으로 답할 수 있으면 제외한다. 현재 프로젝트의 제약, 특정 입력·상태, 단계 간 연결, 실패 시 실제 처리 등 답에 필요한 프로젝트 맥락을 질문에 넣는다.
4. 중요한 설계 선택은 코드로 확인되지만 선택 이유나 검토한 대안이 로그에 없으면, 그 이유나 당시 고려한 대안을 사용자에게 설명하도록 묻는다. 근거를 지어내거나 대안을 검토했다고 가정하지 않는다. 기록과 코드가 어긋나면 실제 구현을 기준으로 질문하고, 판단 근거는 답변을 받은 뒤 확인 가능한 기록과 대조한다.
5. 질문과 확인한 코드 위치를 **한 번에 하나만** 제시한다. 정답, 모범답안, 코드 위치가 입증하는 동작에 대한 설명은 사용자가 답하기 전에는 공개하지 않는다. 현재 질문에 대한 사용자의 답을 기다린다.

### 질문 예시

10/31 실제 시험 질문을 기억에 따라 정리한 예시다. 이 정도의 구체성과 깊이를 기준으로 현재 프로젝트에서 확인한 기능, 단계, 경계 또는 실패 조건을 넣어 변형한다. 계획·실행 분리나 retry·fallback 같은 구조는 실제 코드에 있을 때만 그 동작을 묻는다.

- **구현 방식 및 대안** — 이 핵심 기능에서 현재 방식을 선택한 이유는 무엇인가? 고려한 대안이 있다면 이 프로젝트의 요구사항과 제약에 비춰 각 방식의 장단점을 비교해 달라.
- **전체 파이프라인** — 이 입력이 최종 출력까지 어떤 단계를 거치는가? 각 단계가 무엇을 받고 넘기며, 왜 그렇게 연결했는가?
- **Planning / Execution** — 이 시스템에서 계획과 실행의 책임은 어디에서 갈리는가? 두 단계 사이에 어떤 정보를 어떤 방식으로 전달하며, 왜 분리했는가?
- **예외 처리** — 확인한 파이프라인의 특정 단계에서 이 입력이나 실패 조건이 발생하면 이후 흐름과 상태는 실제로 어떻게 바뀌는가? 왜 그렇게 처리했는가?

## JUDGE — 사용자 답변 검증

1. 현재 질문에 대한 사용자의 실제 답변을 받은 뒤 검증한다. 답변이 없으면 기다리고, 의미가 불명확하면 해당 질문에 대한 보충 설명을 하나 요청한다.
2. 질문의 코드 위치와 관련 호출부를 다시 확인하고, 답변의 주장과 실제 코드의 동작을 대조한다. 설계 이유, 대안, 승인, 실행 결과는 확인된 로그·검증 근거와 따로 대조한다.
3. 잘못 이해한 부분과 답변에 빠진 핵심을 구분해 관련 `파일:줄`과 함께 짚는다. 로그나 실행 증거가 부족한 주장은 미확인으로 표시한다. 답이 근거와 일치하면 그렇게 알려준다. 사용자를 대신해 답변을 완성하거나 점수를 계산하지 않는다.
4. 현재 답변에 대한 피드백을 마친 뒤 연습을 계속할 때 다음 질문을 하나 제시한다. 보충 답변이 필요하면 현재 질문에 머문다.
